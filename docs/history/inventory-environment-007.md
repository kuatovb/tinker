- **Реализованная функциональность основы (офлайн Python API)**:
  - `CollaborationCoordinator` реализует офлайн-операции `create` и `approve` с механизмом *durable request intent*: предварительная запись намерения (`status="in_progress"`, `payload_digest`, детерминированные UUID и ожидаемая ревизия) под файловой блокировкой `msvcrt.locking` исключает создание дублирующих UUID заданий или зависших несогласованных ревизий (`dangling approvals`) при аварийных сбоях и повторах. При несовпадении параметров или нарушении целостности запись не подменяется, а генерирует ошибку (`corruption_detected` или `request_conflict`).
  - Строгая валидация определений задач: парсинг чекбоксов `- [ ] Tnnn` / `- [x] Tnnn` производится исключительно из явного артефакта задач (`tasks.md`), строго в кодировке UTF-8; произвольные текстовые упоминания и ссылки без определений отклоняются.
  - Доверенные идентификаторы источников решений человека: `VALID_HUMAN_SOURCES = {"human user", "human_user", "user_ui", "web_ui", "terminal_user", "cli_user"}` с источником по умолчанию `'human user'`. Перечисление синтаксически отсекает произвольные строки ботов, но не является криптографическим доказательством присутствия человека: фактический выбор человека обязан собирать и передавать вызывающий хост / Codex.
  - Защита от утечек чувствительных данных: статус `sensitive_output_blocked` блокирует попытки согласования и записи секретов/токенов в журнал событий, запросы и отчёты.
  - Единая политика безопасности путей: проверка символических ссылок и канонизация путей до чтения, исключение абсолютных путей хоста из переносимого состояния, сохранение целостности Git baseline при staged-переименованиях и конфликтах слияния.
- **Фоновый запуск и изолированный наблюдатель (`CollaborationCoordinator.start` + `worker_main`)**:
  - Метод `CollaborationCoordinator.start` возвращает `work_id` и `turn_id` программы-исполнителя без ожидания завершения фонового хода (отклик < 2.0 с подтверждён в контролируемом тесте с fake CLI; для нативных синхронных вызовов квоты действует ограниченный IO таймаут).
  - Предварительная фиксация намерения запуска (`status="in_progress"`), CAS-резервирование исполнителя (`worker_token`) и создание структуры хода (`Turn с UUID turn_id`) выполняются под блокировкой `msvcrt.locking` до создания дочернего процесса (`Popen`). Повторный запрос при наличии активного хода возвращает детерминированный ответ без повторного запуска процесса; повтор при неизвестном резервировании возвращает `execution_unknown`.
  - Фоновый наблюдатель `scripts/ai/collaboration/worker_main.py` запускается в отсоединённом режиме (`subprocess.DETACHED_PROCESS | subprocess.CREATE_NO_WINDOW`, без shell) через локально определённый Python-интерпретатор (с возможностью переопределения и fallback на `sys.executable`) и явные аргументы `argv`.
  - Разрешение Windows venv redirector lineage: процедура `verify_process_lineage` проверяет direct PID либо `os.getppid` непосредственного родителя-лаунчера и точное время создания (`creation_time` через `GetProcessTimes`), токены задания и хода без обхода окружения; `child_env` локально настраивает корень `PYTHONPATH`, сохраняя системные настройки.
  - Модель блокировок: монопольная файловая блокировка `execution.lock` удерживается процессом наблюдателя на всё время хода; короткая блокировка `ownership.lock` защищает атомарные CAS-операции резервирования в `reservation.json` (снимки состояния и события защищаются `store.lock` отдельно).
  - Семантика состояний жизненного цикла: статус `SUCCESS` выставляется только при наличии терминального результата с валидированным `structured_output`, нормальном коде завершения процесса (код 0), получении сигналов EOF от обоих потоков чтения (stdout/stderr) и отсутствии ошибок доступа (`permission_denied`), фатальных ошибок и незавершённых действий (pending tools). Задание переходит в состояние `in_review` (не `complete`), резервирование удерживается до независимого ревью и согласования.
  - Обработка тайм-аута: перевод в статус `execution_unknown` с продолжением наблюдения исходного процесса до его фактического выхода И закрытия обоих потоков чтения (readers EOF) без немедленного `kill` или повторного запуска. Незавершённые действия сохраняют `execution_unknown` и требуют ручного восстановления; запоздалый результат выставляет флаг `requires_reconcile=True`, а резервирование не сбрасывается автоматически (no auto-release).
  - Остановка по сигналу `stop`: выполняется на границе хода (а не отдельных шагов); активный процесс не объявляется остановленным до завершения, промежуточные данные сохраняются.
- **Контроль квот Antigravity (US7 / T048, T049/T051 частично)**:
  - Read-only адаптер лимитов вызывает нативный CLI с аргументами со слэшем: `agy -p /model --output-format json` и `agy -p /usage --output-format json`; в JSON-ответе возвращается `command.name="model"` и `command.name="usage"` без слэша.
  - Подтверждён нулевой расход модельных ходов и токенов (`num_turns=0`, `total_tokens=0`).
  - Фоновый периодический монитор остатка квот во время длительного хода: интервал проверки 60 с, порог малого остатка 20% (0.20).
  - Проверка остатка выполняется перед генерацией промпта и в процессе выполнения; состояния `quota_low`, `quota_exhausted` или `quota_unknown` блокируют следующий генерирующий ход.
  - Дедуплицированные безопасные уведомления (`quota_notice`) исключают спам повторными записями.
  - Ошибки ввода-вывода при сохранении снимка квоты вызывают `checkpoint_error` и не маскируются успешным статусом.
  - До интеграции MCP Codex выполняет ручную проверку реальной квоты перед каждым пакетом CLI-команд. Модель на ход: `gemini-3.8-flash-high`, глобальные настройки и платные опции не изменяются.

- **Архитектура моста, границы реализации и ограничения**:
  1. Архитектурная модель: мост реализуется как Python-сервер на базе MCP SDK (`from mcp.server import MCPServer`) по протоколу stdio (`collaboration_bridge.py serve`), к которому Codex подключается как MCP-клиент, транслирующий вызовы в Antigravity CLI. Взаимодействие не использует MCP sampling или прямые вызовы API OpenAI.
  2. Запуск процесса исполнителя: программный API `CollaborationCoordinator.start` реализован для автономного вызова; в интерфейсе CLI команды `start` нет в парсере аргументов, инструменты MCP-сервера ещё не подключены.
  3. Команды-заглушки: команды CLI `bootstrap`, `serve`, `handoff`, `export`, `reconcile`, `recover` возвращают явные заглушки с сообщением об ожидании последующих этапов.
  4. Регистрация bootstrap: конфигурация нативного Antigravity никогда не модифицируется мостом. Будущий bootstrap настраивает подключение моста исключительно в локальной конфигурации MCP-клиента Codex.
  5. Сквозные живые E2E-тесты взаимодействия агентов и тесты на втором Windows-устройстве не проводились.
  6. Самостоятельный режим Antigravity остаётся полностью независимым и не требует запущенного моста или доступности Codex.
  7. GitHub MCP не подключён: отсутствует системная переменная `GITHUB_PERSONAL_ACCESS_TOKEN`. Для локальных сборок и тестов токен не требуется.
