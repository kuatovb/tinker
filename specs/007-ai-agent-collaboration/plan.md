# План разработки tinker

**Ветка:** main. **Спецификация:** [spec.md](spec.md). **Статус:** разработка отложена, подтверждены 8 из 57 задач. Перед продолжением необходимы сверка фактического кода и отдельное поручение пользователя.

## Результат и подход

Codex передаёт согласованные задания через локальный MCP-инструмент. Python worker запускает Antigravity CLI, сохраняет результат и возвращает вопрос либо отчёт. Codex отвечает и отправляет замечания в конкретную сессию исполнителя. Успех исполнителя означает готовность к независимой проверке; завершение подтверждает Codex.

Мост подключается только к Codex. Самостоятельный Antigravity не обязан ждать Codex, использовать мост или проходить его ревью. Контекст передачи — обычный Markdown, доступный без модели Codex и без Python/MCP. Возврат Codex начинается со сверки Git и кода.

## Технический контекст

| Параметр | Решение |
|---|---|
| Платформа | Локальные Windows 10/11 checkout; Linux/macOS в первой версии не заявляются |
| Язык | Python 3.12+; установленный Python 3.12 поддерживается |
| Зависимости | Отдельное окружение моста, официальный `mcp==2.3.0` — стабильная версия на дату проверки; остальное — стандартная библиотека |
| CLI | Проверены Codex 0.160.0 и Antigravity 1.2.16; bootstrap проверяет необходимые флаги, не обновляет CLI автоматически |
| Интерфейс | MCP stdio только для Codex; самостоятельный CLI для статуса, остановки, передачи и сверки |
| Исполнитель | Native `agy.exe`, NDJSON; один ход на процесс, точный `--conversation` при продолжении |
| Хранилище | UTF-8 JSON-снимки, нормализованный журнал и Markdown в игнорируемом `logs/ai/collaboration/`; без БД |
| Проверки | `unittest`, контрактные фикстуры, MCP handshake и небольшие реальные E2E в отдельных копиях |
| Отклик | Цель локального status — до 2 секунд; start возвращает work_id после checkpoint, не ждёт модель; read wait до 30 секунд |
| Масштаб | Несколько работ с разными ID; последовательная запись одной копии, параллельная реализация в отдельных checkout |

Начальный срок хода — 600 секунд, задаётся положительным параметром задания и контролируется внешними monotonic часами. Срок MCP polling отличается от срока исполнения. Таймаут не освобождает checkout для второго исполнителя.

Если задание относится к Android, doctor дополнительно проверяет JDK и SDK текущего устройства. Версии Gradle и плагинов задаёт рабочий проект; мост их не обновляет.

## Порядок работы

1. `doctor` определяет текущий Git root, native executables и необходимые возможности без обращения к моделям. `bootstrap --dry-run` показывает локальные изменения; применение регистрирует только собственный MCP server в Codex.
2. Codex формирует задание из согласованных spec/plan/tasks, сохраняет доказательство согласования объёма и baseline Git. `start` отклоняет задание без согласования либо с конфликтующим владельцем checkout.
3. Durable checkpoint и handoff.md записаны до запуска. Отдельный worker получает одну инструкцию через stdin; `--json-schema` задаёт объект вопроса/результата/блокировки. EOF отправляется после сообщения, процесс завершает текущий ход. Worker продолжает собирать результат при закрытии Codex.
4. Ограничения и фактическое решение пользователя передаются в задании. `--mode accept-edits` действует только на этот запуск; shell/MCP permissions не расширяются. Если исходный workflow Antigravity требует нового согласования, он возвращает блокировку, одобрение не имитируется.
5. Вопрос сохраняется с message_id. Codex отправляет answer с этим ID, новой turn_id и прежним conversation_id. Новый объём или права ожидают пользователя.
6. Отчёт переводит работу в in_review. Codex сравнивает фактический diff с baseline, проверяет критерии и заявленные тесты. Review fixes возвращаются в ту же сессию. Отметки исполнителя считаются заявлениями; подтверждённые отметки задач ссылаются на evidence Codex.
7. `complete` допустим после принятого ревью текущей ревизии файлов. Коммит/push выполняет Codex по обычным правилам проекта, мост их сам не делает.

## Контроль квоты Antigravity

`environment.py` получает отдельные read-only отчёты `agy -p /model --output-format json` и `agy -p /usage --output-format json`, вне stream-input и без prompt к модели. Выбранная модель определяется из per-run override либо текущего `/model`; её группа проверяется явно. Session usage/counters не заменяют квоту аккаунта. Один источник относится к конкретному device/account context, но identity/auth в журнал не включаются.

Проверенный ответ CLI 1.2.16 содержит `command.data.groups[].buckets[]`: `remaining_fraction`, `reset_time`, `window`, `id/name`; `/model` — `command.data.id/label/effort/is_default`. Нормализуются только нужные safe поля, недоступные значения — null. Строки ошибок/неожиданная schema не интерпретируются как полный остаток; устаревший reset/неизвестная группа дают quota_unknown. Источник bounded отдельным внешним timeout, без изменения permissions или settings Antigravity.

Свежая проверка нужна перед start/reply/review fixes/resume. Во время активного хода worker проверяет раз в 60 секунд; snapshot старше 60 секунд не разрешает новый ход без обновления. Минимальный остаток среди применимых окон <=20% даёт quota_low, 0 или подтверждённая ошибка квоты — quota_exhausted. Недоступный источник/неверная группа — quota_unknown. Во всех трёх случаях новый ход запрещён; существующий writer не объявляется остановленным только по квоте. Ход прекращается по прежнему безопасному протоколу, без обещания остановить внутренние обращения CLI посреди операции.

До автоматического адаптера Codex выполняет эти read-only проверки сам перед заданиями Antigravity и между этапами. Они обязательны также при создании самого моста; quota guard входит в полный MVP, а базовая передача без него называется лишь техническим прототипом.

На событие квоты записывается checkpoint/handoff.md из уже сохранённых данных: task/work IDs, последние достоверные события, фактические пути и fingerprint/Git metadata, проверенные и незавершённые действия. Codex сверяет evidence и уведомляет пользователя в текущем диалоге; worker возвращает событие через MCP read. Повторяющееся одинаковое предупреждение не дублируется, новое исчерпание/потеря источника видны отдельно. Без доступного Codex остаётся durable запись для offline status, а не обещание нового ответа его модели. Внешние сообщения/автоматизации не создаются.

Продолжение — по пользовательскому решению после свежей quota check и reconcile; не менять автоматически модель/аккаунт, paid credits или global policy. Детали проверки источника и его ограничений — в [research.md](research.md).

## Владение checkout и остановка

Ключ checkout — канонический Git worktree root, с нормализацией регистра и разрешением junction/symlink. Разные worktree имеют разные ключи. Windows file lock защищает изменения состояния; worker держит execution lock до подтверждённого завершения хода. Сохранённая reservation по work_id защищает интервалы вопрос/ответ и ревью. Чужая reservation означает checkout_busy. PID проверяется вместе с временем запуска и worker token.

Baseline фиксирует HEAD, ветку, staged/unstaged/untracked пути и раздельные index/worktree fingerprints всех затрагиваемых несекретных файлов, включая уже изменённые посторонние файлы и untracked. Учитываются существование, создание/удаление и staged blob ID. Уже изменённые посторонние файлы не передаются на запись; изменение такого файла проверяется по fingerprint, а не только набору путей. Секретные файлы не читаются: для них фиксируются доступные Git/файловые metadata; подозрительное изменение требует отдельной безопасной проверки и блокирует принятие. После каждого хода проверяется фактический scope diff. Границы задания и проверка diff не являются ОС-песочницей: для жёсткой изоляции нужен отдельный checkout с действующими разрешениями среды.

Остановка первой версии происходит на границе текущего хода: следующие инструкции запрещены сразу, текущий ход должен завершиться. Stop request доступен offline через CLI. Таймаут/crash без однозначного завершения оставляет execution_unknown; новый writer, retry и handoff блокируются до проверки реального состояния. Принудительное убийство CLI не доказывает остановку всех сторонних операций. Ручная проверка активного исполнителя, запись подтверждения и сверка Git позволяют закрыть неопределённость; stale lock по возрасту автоматически не снимается.

Мост координирует собственные процессы, а не произвольные редакторы. Перед native работой пользователь завершает безопасную передачу. После неё reservation освобождена; установка моста и доступность Codex для самостоятельного Antigravity не нужны.

## Переносимость и продолжение без Codex

Корень — проверенный локальный override или `git rev-parse --show-toplevel`, сверенный с расположением скрипта. CLI — PATH или проверенный override. Native executable получает список аргументов, текст задания идёт stdin. `.cmd/.bat` launcher не принимается молча: doctor просит native EXE.

В Git входят относительные ссылки и исходники bootstrap. Локальная регистрация содержит абсолютные пути только этого устройства. Имя MCP-записи устойчиво для копии, повторный bootstrap — no-op; чужая запись с тем же именем вызывает коллизию. При переносе каталога bootstrap выполняется заново. Модели, профили и другие MCP-записи сохраняются. Java/SDK проверяются только при Android-задании; JAVA_HOME автоматически не меняется.

Каждый checkpoint обновляет handoff.md: цель, ссылки, готовые и незавершённые действия, проверки, граница текущей операции и необходимость сверки. Файл строится из имеющихся данных без вызова модели. При недоступном Codex пользователь читает его и запрашивает offline handoff. Native продолжение начинается после подтверждения safe handoff: исполнитель и известные операции завершены, свежий checkpoint сохранён, reservation освобождена. Одного ожидания CLI exit недостаточно. Без установленного моста доступны spec/plan/tasks и ранее сохранённый handoff.md; если в нём нет подтверждения безопасной передачи, пользователь сначала проверяет отсутствие прежнего исполнителя и незавершённых операций, сохраняет подтверждение восстановления и сверяет Git.

На другое устройство код и согласованные артефакты передаются через Git. Safe export копирует выбранный контекст отдельно, по умолчанию в игнорируемый каталог, без автопубликации. Полный журнал, авторизация, абсолютные пути и session ID в экспорт не входят. Новое устройство создаёт новую локальную сессию после сверки кода.

После native работы `reconcile` показывает актуальный HEAD/diff, отметки tasks и результаты пользователя. Работа остаётся на проверке до решения Codex о выполненных действиях и свежего согласования на остаток. Старые complete/approval не применяются автоматически к изменённой ревизии.
